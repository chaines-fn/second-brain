## Integration Patterns & Gotchas

**Per-WO vs. project-level dispatch:** The current per-WO trigger is intentional — it provides immediate response and per-WO `dispatch_run_id` for status tracking. Moving to project-level would require buyers to poll for failures instead of getting synchronous feedback. Linda Lo is strongly opposed to losing this visibility.

**Project names are not unique per buyer:** Multiple projects can share the same name across different IDs (confirmed by Linda Lo with a Fujitsu/color retail imaging example, Apr 7 2026). Using project name as an identifier in integrations is a non-starter — must use project ID. Watch for this if any integration passes project by name (e.g., Belos integration flagged as doing this — Chuck to follow up).

**Feature flags:** `ENABLED_AUTOMATED_DISPATCH` and `DA_MARKETPLACE_EXPANSION` are Split.io flags at company level. Marketplace expansion is separately gated by contract flag, not just Split.io.

**Dispatch status protobuf design (Chuck):** Schema separates status vs. outcome vs. outcome action — important distinction when reading events downstream. Don't conflate these.

**fn-core trigger:** Smart dispatch is triggered by `POST v2/workorders/smart-dispatch` in fn-core, which hands off to dispatch-automation. fn-core remains source of truth for WO state.

**RIMG auto-trigger implementation detail (Apr 10, 2026):** Feature flag checked in FnCore during WO creation.
