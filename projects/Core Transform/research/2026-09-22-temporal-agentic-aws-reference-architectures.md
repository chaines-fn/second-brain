# Temporal as Orchestration for Customer-Facing Agentic AI on AWS

**Research question:** What do current (2025-2026) reference architectures look like for using Temporal to orchestrate customer-facing agentic AI solutions on AWS, and how does that fit Pearl's tech direction (PydanticAI, Bedrock, EKS as the leading runtime candidate)?
**Date:** 2026-09-22
**Scope:** Reference architectures and integration patterns for Temporal + AWS agentic AI, with emphasis on PydanticAI-Temporal integration and Temporal-on-EKS vs Bedrock AgentCore Runtime tradeoffs. Excludes a deep dive on agent memory or MCP gateway topics, which are already tracked separately in tech-context.md.

---

## Summary

Temporal's role in agentic AI has solidified fast over the past year, and it's now a well-worn pattern rather than an experimental one. The core idea repeated across every source: an agent's "reasoning loop" (the loop that decides what to do next) should run as a Temporal Workflow, which is deterministic coordination code, while every non-deterministic or I/O-bound step (the actual LLM call, a tool call, an external API call) runs as a Temporal Activity with its own retry policy. This gives you durability across worker crashes and deploys, native handling of the "wait for a human" problem, and full replay history for audit, all without a state machine you build and maintain yourself. Retool and Block (Cash App's parent) both run production, customer-facing agent products this way at real scale, which is reasonably strong validation that this pattern holds up outside of vendor blog posts.

The more useful finding for Pearl specifically is that there are two distinct "official" reference architectures floating around right now, and they point in different directions. AWS and Temporal jointly published a pattern (as recently as September 21, the day before this research) where a Temporal Serverless Worker runs *inside* Bedrock AgentCore Runtime, using Strands Agents as the agent framework. That's AWS's preferred showcase, but it's built on Strands, which Pearl explicitly ruled out. Separately, PydanticAI has its own native Temporal integration (`TemporalDurability`), documented directly on Pydantic's docs site, that has nothing to do with AgentCore Runtime at all: the Temporal Worker is just a Worker, and it can run anywhere you can run a long-lived process, including EKS. This means Pearl's PydanticAI + Temporal Cloud + EKS lean is a coherent, well-supported combination on its own; it just isn't the one AWS is marketing as "the" reference architecture, because that one is built for Strands. Nothing suggests PydanticAI-on-Temporal running inside AgentCore Runtime specifically has been documented by anyone yet, so if EKS vs AgentCore Runtime comes down to that combination, this is a gap to test rather than something to trust a blog post on.

On EKS vs AgentCore Runtime as a home for the Temporal Worker itself: the tradeoff is the standard managed-vs-self-managed one. AgentCore Runtime gives you serverless scaling and no idle compute cost, but it's a newer surface, tied to Strands in AWS's own examples, and adds a second orchestration layer on top of Temporal's own. EKS gives Pearl full control over the worker, fits the team's existing EKS lean and Mike Mueller's preference for keeping the surface area a small platform team can operate, and every production example that names its infrastructure (Retool, Block) runs workers on conventional compute, not AgentCore Runtime. Also worth noting: at least one AWS reference architecture for multi-agent financial services on EKS + AgentCore (published June 2026) skips Temporal entirely and orchestrates in-process using A2A and MCP instead, backed by AgentCore Memory and Code Interpreter. That's a real alternative pattern AWS is also promoting, not just Strands vs PydanticAI, and it's a useful data point that "durable execution via Temporal" isn't the only AWS-endorsed shape for this problem.

## Findings

### The core pattern: workflow as coordinator, activities as I/O

Every source, official and third-party, converges on the same shape. The Temporal Workflow contains the agent's decision loop and must stay deterministic; it never talks to a model, a tool, or the network directly. Everything that does (the LLM call, each tool invocation, MCP server calls) runs as a separate Activity with its own timeout and retry policy. This split is what buys durability: if a Worker crashes mid-reasoning-loop, Temporal reconstructs the Workflow's state from event history on another Worker and picks up exactly where it left off, without re-running completed steps or re-invoking the LLM. The AWS Partner Network's writeup on AgentCore + Temporal put it plainly: "Temporal activities facilitate durability through event sourcing, persisting each workflow step as an immutable event so that completed actions aren't re-executed."

The Xgrid "11 production pitfalls" piece is a useful counterweight here because it's specific about how teams get this wrong in practice: putting LLM calls directly in workflow code (breaks determinism on replay), wrapping an entire ReAct loop inside one Activity instead of one Activity per tool call (loses granular durability, so a failure on iteration 47 restarts from iteration 1), skipping heartbeats on long-running inference activities, and not setting a timeout on human-approval waits. These aren't theoretical; the piece frames them as the two or three failure classes most teams hit within months of shipping. Worth treating as a checklist before Pearl commits to an implementation pattern, not just background reading.

### PydanticAI's native Temporal integration

Pydantic's own docs (`pydantic.dev/docs/ai/capabilities/durable_execution/temporal/`) describe a clean mechanism: you attach a `TemporalDurability` capability to a standard `Agent`, and outside a workflow the agent behaves normally, while inside a workflow every model call and tool call is transparently routed through Temporal Activities. Tool calls that have argument validators get a separate validation activity. Model requests get their own activity with configurable timeouts (`ActivityConfig`, defaulting to a 60-second start-to-close timeout), and retries stack on top of whatever retry behavior the model SDK and transport layer already do; certain error types (user errors, unexpected model behavior) are explicitly marked non-retryable to avoid infinite retry loops. MCP toolsets get reconnected inside every activity execution, since the worker executing an activity may not be the same process that started the workflow.

Two constraints worth flagging for Pearl's design: Temporal enforces a 2MB default payload limit per direction (base64-encoded binary eats roughly 75% of that budget fast), and the docs point to an external storage hook for offloading large tool outputs or images rather than passing them through workflow/activity payloads directly. The "11 pitfalls" piece calls this the "claim check pattern": store the large output in S3 and pass a reference through Temporal instead of the payload itself. Given Pearl's plan to route media, documents, or long transcripts through agent tool calls, this is a design decision to make early rather than retrofit.

The docs list Bedrock as a supported model provider with no Bedrock-specific caveats beyond the standard model-request wrapping. That's a mild positive signal (nothing Bedrock-specific breaks the pattern) but also means there's no Bedrock-tuned guidance to lean on; the team should assume standard PydanticAI + Temporal behavior applies without a Bedrock-specific safety net.

### AWS's own reference architecture: Strands + Temporal Serverless Workers inside AgentCore Runtime

Published September 21, 2026 (literally the day before this research), Temporal's blog describes a specific, named architecture: a Temporal Workflow acts as the durable agent loop, Strands Agents provides the agent programming model that turns model/tool calls into Temporal Activities, and those Activities run inside AgentCore Runtime, a serverless compute environment that hosts a Temporal Worker. A "Worker Controller Instance" dynamically invokes more AgentCore Runtime sessions as task queue demand grows, and AgentCore's Code Interpreter handles sandboxed tool execution (arbitrary Python, etc). The pitch is elastic, pay-per-use compute with no idle-CPU charges during the long I/O waits typical of agent loops.

This is a real, current, jointly-endorsed pattern, and it's worth taking seriously as a signal of where AWS wants Temporal customers to land. But it's built specifically on Strands, which Pearl decided against on 2026-04-14 (per tech-context.md), and there's no equivalent published pattern substituting PydanticAI into the AgentCore Runtime slot. It's plausible that would work (PydanticAI's Temporal integration doesn't care what compute the Worker runs on), but "plausible" and "documented and validated" are different things, and this would need a spike rather than a citation if Pearl wants to run PydanticAI workers on AgentCore Runtime specifically.

### EKS vs AgentCore Runtime as the Temporal Worker's home

This is the least directly documented of the three focus areas. AWS's own dedicated "Well-Architected perspective" comparing the two (`builder.aws.com/.../running-ai-agents-on-eks-vs-amazon-bedrock-agentcore-a-well-architected-perspective`) exists but its content is behind client-side rendering that this research couldn't extract; treat that as a gap, not a finding, and it's worth having someone open it directly in a browser.

What can be said from what did come through: this is fundamentally the same managed-vs-self-managed tradeoff as any AWS compute decision, just applied to hosting a Temporal Worker. AgentCore Runtime brings serverless elasticity (per the September 2026 architecture, sessions can now run up to 14 days on dedicated EC2-backed compute including GPU and memory-optimized instances, as of the August 2026 AgentCore updates) and no idle cost. EKS brings full operational control, no dependency on a newer AWS service whose primary documented pairing is a framework Pearl rejected, and consistency with the rest of Pearl's infrastructure lean. Every named production case study that specifies its infrastructure (Retool, Block/kgoose) runs on conventional compute (their own Kubernetes/container infrastructure), not AgentCore Runtime, though neither confirms EKS by name.

The one real counter-signal here is the June 2026 AWS blog on multi-agent financial services systems, which explicitly chooses EKS Auto Mode as the base and layers in AgentCore Memory, Code Interpreter, and Browser as targeted managed services rather than running the whole agent loop through AgentCore Runtime, and doesn't use Temporal at all (it relies on the Agent-to-Agent protocol and MCP for coordination, with ArgoCD/Crossplane for lifecycle management). That's directly aligned with the "component-level AgentCore adoption, not wholesale" principle already in tech-context.md, and it's a second real-world validation of running on EKS while cherry-picking specific AgentCore services, independent of the Temporal question.

### Temporal vs Step Functions for this use case

Since Step Functions is AWS's own native alternative, it's worth a direct note even though Pearl has already leaned toward Temporal. The practical tradeoffs: Step Functions is fully managed with no infrastructure to run, priced per state transition ($0.025/1,000 for Standard workflows), and its new Bedrock AgentCore harness integration is explicitly request-response only with a 15-minute task limit, which one comparative analysis called out as "insufficient for extended agent reasoning" such as multi-step tool loops or open-ended approval waits. Temporal requires running and scaling worker infrastructure yourself (unless using Temporal Cloud, which still requires operating the workers, just not the Temporal service), costs $25 per million actions plus storage on Temporal Cloud with a $200/month minimum, but supports code-based activities, sub-second timer granularity, and no hard ceiling on how long a workflow can reason or wait. For an agent loop with unpredictable iteration counts and long human-approval waits, which is exactly Pearl's customer-facing use case, Step Functions' 15-minute ceiling is a real functional blocker, not just a cost tradeoff. This supports the direction already taken rather than changing it.

### Human-in-the-loop pattern

Temporal's documented pattern (both the official AI Cookbook and third-party writeups converge here) uses Signals to inject an external approval decision into a workflow that's paused on `wait_condition()`. The workflow can sit idle for hours, days, or indefinitely, consuming no compute while waiting, and a timeout parameter on the wait ensures the workflow doesn't hang forever if the approver never responds, it instead resolves to a timeout outcome that the workflow logic can act on (auto-reject, escalate, notify a backup approver). Every source treats an unbounded approval wait as a production bug, not an edge case, which lines up with the pitfalls list above. This is directly relevant to Pearl's 1% error-tolerance requirement on financial/assignment decisions and to the guardrails/policy layer already being scoped in tech-context.md.

### Production evidence at customer-facing scale

Two named, credible production deployments stand out. Retool runs its Agents product with each agent run as a Temporal Workflow; their own account is that Temporal was a prerequisite they didn't want to re-litigate ("there are some things you just want to take as a given"), and a roughly ten-person team ships and operates thousands of agent runs daily on Temporal Cloud, without a dedicated ops team for the durability layer. Block (Cash App's parent) runs a materially larger deployment: an internal framework called "kgoose" built on Temporal workflows processes over 100 million weekly activities across Cash App's "Money Bot" (peer-to-peer payment guidance) and Square's "Manager Bot" (merchant business intelligence), sustaining 10,000+ concurrent workflows. Their stated architectural principle, "separate orchestration from data," keeps Temporal itself lightweight (orchestration and durability only) while storing actual session/message state in DynamoDB, activities executing the LLM calls and tool invocations against that external state. Both are regulated-industry, customer-facing, high-stakes use cases (payments, financial guidance), which is a closer analogue to Pearl's use case than most generic agent demos.

## Key uncertainties

The single biggest open question for Pearl specifically: nobody has published a reference architecture combining PydanticAI's native Temporal integration with Bedrock AgentCore Runtime as the worker host. AWS's newest joint reference architecture (Strands + AgentCore Runtime) and PydanticAI's own Temporal docs are two separate, non-overlapping stories right now. If EKS vs AgentCore Runtime is still genuinely open for Pearl, this specific combination should be treated as unvalidated and worth a small spike rather than assumed to work from these sources alone.

The "Temporal Agent Harness" (a wrapper layer Temporal announced in August 2026 that sits above PydanticAI, OpenAI Agents SDK, or Strands to add approval policies and governance) is explicitly pre-release; the authors describe it as inviting feedback rather than production-ready, and its APIs are expected to change. Worth tracking, not adopting yet.

The dedicated AWS "Well-Architected perspective" comparing EKS and AgentCore Runtime specifically couldn't be retrieved (client-side rendering blocked extraction); this is likely the single most directly relevant document to the EKS-vs-AgentCore question and is worth having someone pull up directly rather than relying on this report's secondhand coverage of the topic.

Given how fast this space is moving (the flagship Temporal + AgentCore architecture is one day old as of this writing, and Replay 2026's major announcements landed in May 2026), assume some of this shifts again within a quarter. The general orchestration pattern (workflow as loop, activities as I/O, signals for approval) looks stable across a year of sources and multiple production deployments; the specific AWS service pairings (which AgentCore components, which compute host) are the part most likely to keep moving.
