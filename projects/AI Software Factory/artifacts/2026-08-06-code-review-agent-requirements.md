## Purpose and boundaries

| ID | Requirement |
|---|---|
| **CR-1** | The system MUST deliver two separable capabilities: a **review agent** producing findings and a coverage record, and a **merge gate** producing a readiness verdict. |
| **CR-2** | The gate verdict MUST be a function of an independent risk signal and the review's findings. It MUST NOT be derived solely from the reviewer's own assessment of its work. *(Prevents "I found nothing, therefore ship it.")* |
| **CR-3** | The agent MUST NOT execute code, tests, or builds. |
| **CR-4** | The agent MUST NOT require a sandbox reproducing any FN runtime environment. |
| **CR-5** | The agent MUST NOT read CI results or Sonar findings. Merge composition is GitHub's job via branch protection. |
| **CR-6** | Review dimensions MUST be scoped away from Sonar's deterministic lane (static patterns, lint rules, security pattern matching) to avoid duplicate findings from two bots. |
| **CR-7** | The agent MUST publish what it examined, what it judged fine, and what it did not check. This is the primary differentiator and is not optional. |
| **CR-8** | Coverage claims MUST be emitted from the pipeline's actual execution. They MUST NOT be generated by a model summarizing its own behavior. |

## Trigger

| ID | Requirement |
|---|---|
| **CR-10** | MUST trigger on `pull_request.opened` (non-draft), `ready_for_review`, `synchronize`, and `reopened`. |
| **CR-11** | MUST support an on-demand `@fn-review` comment command. |
| **CR-12** | MUST skip draft PRs entirely. |
| **CR-13** | MUST skip bot-authored dependency PRs by default. |
| **CR-14** | MUST debounce `synchronize` events (~60s) so a push burst produces one review. |
| **CR-15** | On `synchronize`, MUST perform an incremental review (new commits plus re-check of previously raised open findings) rather than a full re-review. |
| **CR-16** | MUST be delivered via GitHub App webhook. MUST NOT require any file, workflow, or config committed into product repos. |
| **CR-17** | MUST deduplicate concurrent events for the same PR and assign a correlation ID per run. |

## Review dimensions

| ID | Requirement |
|---|---|
| **CR-20** | The pipeline MUST be a fixed graph of named dimensions. A free-form agent loop is prohibited as the outer structure. |
| **CR-21** | Dimensions MAY use open-ended subagent exploration internally. |
| **CR-22** | v1 dimensions MUST be exactly: (1) AC / ticket intent, (2) Architecture fitness, (3) FN conventions and platform fit, (4) Authorization and data exposure, (5) Test adequacy, (6) Data / schema. |
| **CR-23** | Dimension 3 MUST be scoped to FN-specific conventions Sonar has no rules for. It MUST NOT duplicate generic lint or style checking. |
| **CR-24** | Dimension 4 MUST be scoped to authorization logic, tenant isolation, and endpoint exposure reasoning. It MUST NOT perform security pattern matching. |
| **CR-25** | Each dimension MUST emit exactly one of: `clean`, `findings`, `not applicable`, `not verifiable`. |
| **CR-26** | `not applicable` and `not verifiable` MUST be distinct from `clean`. `clean` MUST mean "examined and found acceptable." |
| **CR-27** | Each dimension MUST emit a specific, falsifiable description of what it examined. Generic descriptions such as "reviewed acceptance criteria" do not satisfy this. |
| **CR-28** | Each dimension MUST emit a coarse confidence value: high, medium, or low. |
| **CR-29** | Output ordering MUST rank architecture fitness and AC verification above conventions and style. |

## Inputs and context

| ID | Requirement |
|---|---|
| **CR-30** | MUST obtain repo context via tool-based exploration (grep, glob, read, AST, git). MUST NOT depend on a maintained vector index as the primary context mechanism. |
| **CR-31** | MUST resolve the Linear ticket via fallback chain: Linear native PR-issue linkage, then PR title conventional commit scope, then branch name. |
| **CR-32** | If no ticket resolves, dimension 1 MUST report `not verifiable, no ticket identified`. It MUST NOT report `clean`. |
| **CR-33** | If the ticket has no usable acceptance criteria, dimension 1 MUST report `not verifiable` and name the reason. |
| **CR-34** | MUST support linked specs as a dimension 1 input. |
| **CR-35** | MUST support repo ADRs as a dimension 2 input. |
| **CR-36** | MUST degrade gracefully and visibly when specs or ADRs are absent. Absence MUST appear in the output rather than being silently ignored. |
| **CR-37** | MUST load FN shared skills as per-dimension context (`fn-api-design`, `fn-ddl-design`, `fn-event-integration`, and successors). |
| **CR-38** | MUST clone repos shallow and read-only. |

## Output artifact

| ID | Requirement |
|---|---|
| **CR-40** | MUST post exactly one summary comment per PR, updated in place across rounds. |
| **CR-41** | The summary MUST contain a coverage table with columns: Dimension, Verdict, Examined, Confidence. |
| **CR-42** | The summary MUST contain an explicit "not checked" disclosure naming scope limits. |
| **CR-43** | Per-dimension detail MUST be present, collapsed by default, and richer than the table row. |
| **CR-44** | Confidence MUST be expressed categorically. Numeric scores and percentages are prohibited, because a displayed score anchors the reader's own judgment and implies precision that is not present. |
| **CR-45** | Severity taxonomy MUST be exactly: `blocking`, `recommended`, `nit`, `question`. |
| **CR-46** | Every finding MUST have an inline comment on the specific line it concerns. |
| **CR-47** | Every inline comment MUST carry its severity as a visible prefix. |
| **CR-48** | Nits SHOULD post as GitHub suggested changes where mechanically possible. |
| **CR-49** | Nits MUST be capped per PR (~10). Overflow MUST roll into the summary rather than posting inline. |
| **CR-50** | For PRs exceeding the size threshold where review is reliable (~200 to 400 LOC), the agent MUST review anyway, MUST emit an explicit oversized-PR finding, and MUST downgrade gate confidence. |
| **CR-51** | The summary MUST include the run ID in its footer. |
| **CR-52** | The summary MUST include review history for rounds 1..N within the collapsed section. |

## Finding identity and multi-round behavior

| ID | Requirement |
|---|---|
| **CR-60** | Findings MUST have a stable fingerprint that survives line shifts and rebases. |
| **CR-61** | The fingerprint MUST derive from dimension plus finding category plus enclosing symbol plus normalized surrounding code. File path and line number alone are insufficient. |
| **CR-62** | The system MUST NOT re-post an inline comment for a finding already open on the PR. |
| **CR-63** | The system MUST resolve the inline thread when a finding's underlying issue is fixed, and MUST reflect the resolution in the summary. |
| **CR-64** | The system MUST NOT re-raise a finding disputed by a human on that PR. |
| **CR-65** | A delta comment MUST be posted when the verdict materially changes (new blocking findings, or blocking cleared). It MUST NOT be posted on every push, because GitHub does not reliably notify on comment edits. |
| **CR-66** | Fingerprints MUST be the primary key of the durable review record and the feedback store. |

## Merge gate

| ID | Requirement |
|---|---|
| **CR-70** | The gate MUST post its verdict as a GitHub check run. |
| **CR-71** | The gate MUST fail open. On agent error or timeout it MUST report a neutral "review unavailable" state and MUST NOT report failure. |
| **CR-72** | The gate MUST NOT be the sole merge authority. GitHub branch protection composes it with other checks. |
| **CR-73** | The risk score MUST be computed from static change characteristics only: change type, files and paths touched, path criticality, blast radius, diff size, and backward compatibility surface. |
| **CR-74** | The risk score MUST NOT take review findings as input. |
| **CR-75** | The risk score MUST NOT require CI-derived data, including coverage, in v1. |
| **CR-76** | The risk scorer SHOULD be deterministic and non-LLM. |
| **CR-76A** | The risk scorer MUST classify every PR into exactly one of two tiers: `trivial` or `scored`. |
| **CR-76B** | `trivial` MUST be limited to PRs where every changed file is documentation, configuration, or a dependency manifest. Any other file type touched MUST classify the PR as `scored`. |
| **CR-76C** | On `trivial`, the review agent MUST NOT be invoked. |
| **CR-76D** | On `trivial`, the gate MUST post a `skipped` verdict. `skipped` MUST NOT be treated as, or displayed as, `clean`. |
| **CR-76E** | An `@fn-review` comment MUST force a full review regardless of tier and MUST reclassify the PR as `scored` for that run. |
| **CR-77** | v1 MUST ship at tier 1 (advisory). |
| **CR-78** | The system MUST support tier 2 (required check) and tier 3 (auto-merge via GitHub native auto-merge) by design, gated on accumulated evidence. **LATER** for enablement. |
| **CR-79** | A disputed blocking finding MUST move the gate to "needs human adjudication." It MUST NOT move the gate to pass. |

## Feedback and learning

| ID | Requirement |
|---|---|
| **CR-80** | MUST accept `@fn-review disagree: <reason>` as a reply to an inline comment. |
| **CR-81** | MUST accept `@fn-review missed: <description>` as a line-anchored comment. |
| **CR-82** | A reason MUST be required on both. Reaction-only signals MUST NOT be accepted as feedback. |
| **CR-83** | MUST harvest passive signals: finding fixed (positive), thread resolved without code change (probable false positive), finding ignored and merged (weak negative), bot comment reacted with 👎 (weak negative, eval label only). |
| **CR-84** | Passive signals MUST NOT require human triage. They are eval labels. |
| **CR-85** | A dispute MUST immediately silence that finding for the remainder of the current PR, without approval. |
| **CR-86** | A dispute MUST NOT produce any cross-PR behavior change without human triage and approval. |
| **CR-87** | A dispute MUST NOT remove the finding from the summary or the durable record. The record MUST show it as disputed and unresolved. |
| **CR-88** | Any user, including the PR author, MUST be permitted to dispute any finding. Safety comes from CR-86 and CR-87, not from access restriction. |
| **CR-89** | Suppressions MUST be scoped to repo plus fingerprint. Global suppression is prohibited. |
| **CR-90** | Suppressions MUST expire and require re-validation. |
| **CR-91** | Learning MUST be limited to three mechanisms: deterministic suppression, retrieval-time context injection, and promotion to a skill or Sonar rule. |
| **CR-92** | Model fine-tuning MUST NOT be used as a learning mechanism. |
| **CR-93** | Dispute rate per dimension MUST be tracked as a first-class metric. |

## Observability

| ID | Requirement |
|---|---|
| **CR-100** | MUST emit full-content execution traces to a store FN controls. |
| **CR-101** | Traces MUST use AgentCore Observability to CloudWatch as the primary destination. |
| **CR-102** | Full-content trace retention MUST be 30 days, enforced by log-group retention configuration. |
| **CR-103** | Each trace MUST contain: run and session ID bound to PR and commit SHA, a span per dimension node, every tool call with arguments and results, model plus tokens plus cost per node, finding fingerprints emitted, and gate inputs plus computed verdict. |
| **CR-104** | Traces MUST later record the human outcome (merged, disputed, overridden) to serve as eval data. |
| **CR-105** | Content-free spans and metrics MUST be exported to Datadog via ADOT fan-out with a redaction processor. |
| **CR-106** | The run ID MUST equal the AgentCore session ID. |
| **CR-107** | Trace detail MUST NOT be rendered on the PR. Only the run ID appears there. |
| **CR-108** | The durable review record store MUST be separate from the trace store and MUST NOT expire at 30 days. |
| **CR-109** | Enabling Bedrock model invocation logging MUST be treated as an explicit documented decision, with account and region scope understood, because it captures every Bedrock call in the account rather than only this agent's. |

## Security and permissions

| ID | Requirement |
|---|---|
| **CR-110** | The GitHub App MUST request `contents: read`, `pull_requests: write`, and `checks: write`. |
| **CR-111** | The GitHub App MUST NOT request `contents: write` under any circumstances. |
| **CR-112** | The agent MUST NOT push commits, create branches, modify files, or merge PRs. |
| **CR-113** | Read-only access MUST be enforced by the permission boundary, not by prompt instruction. |
| **CR-114** | Models MUST run in-boundary via Bedrock. Code content MUST NOT be sent to any third-party model endpoint. |
| **CR-115** | Webhook payloads MUST be signature verified. |

## Performance and cost

| ID | Requirement |
|---|---|
| **CR-120** | Review latency MUST meet p50 under 5 minutes and p95 under 15 minutes. |
| **CR-121** | A per-PR token budget cap MUST exist before any rollout beyond the pilot. |
| **CR-122** | A per-repo daily run cap MUST exist before any rollout beyond the pilot. |
| **CR-123** | Dimensions resolving to `not applicable` MUST short-circuit without full model invocation. |
| **CR-124** | Per-dimension cost MUST be independently observable. |
| **CR-125** | Language support MUST sequence Go and NestJS first, React and React Native second, and the PHP monolith last. |

## Evaluation

| ID | Requirement |
|---|---|
| **CR-130** | The system MUST support a shadow mode that runs the full pipeline and gate without posting to the PR. |
| **CR-131** | Shadow mode MUST run from phase 0, so gate-graduation evidence accumulates from the start. |
| **CR-132** | MUST support backtesting against already-merged PRs with known outcomes. |
| **CR-133** | MUST measure per-dimension precision on blocking findings. |
| **CR-134** | MUST measure false-negative rate against PRs later reverted or hotfixed. |
| **CR-135** | Per-dimension model selection MUST be decided empirically against FN repos. Model tier MUST NOT be assumed to predict review quality. |
| **CR-136** | The review model family SHOULD differ from the family engineers predominantly author with, to avoid correlated blind spots. |
| **CR-137** | The system MUST report time-to-first-human-decision and open-PR queue depth trends, sourced from the existing repo scorecard pipeline, as a system-level throughput metric alongside per-dimension precision. |

## Explicitly out of scope for v1

| Item | Reason |
|---|---|
| Executing tests or builds | CI owns this |
| Reading CI or Sonar results | GitHub branch protection composes verdicts |
| Any sandbox or runtime-parity environment | Follows from read-only review |
| Static analysis, lint, security pattern matching | Sonar's lane |
| Auto-fixing or committing changes | Permission boundary prohibits it |
| Model fine-tuning | Rejected as a learning mechanism |
| Cross-repo impact analysis | Disclosed under "not checked" instead |
| Pilot repo selection | Deferred to implementation |
