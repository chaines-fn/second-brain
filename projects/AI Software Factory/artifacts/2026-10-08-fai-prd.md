## 1. Summary

Fai is Field Nation's internal software factory. Its first job is to take pre-approved, eligible engineering issues from Linear, run agents in isolated sandboxes to produce pull requests (PRs), and move those PRs through the existing gates (Gitar, Sonar, and human review) to merge. Every run is recorded so that delivery speed, cost, and quality can be measured.

The full vision extends the same model across the software lifecycle, from customer and business signals through shaping, specification, build, verification, deployment, and monitoring, and back into learning. The defining property is one traceable chain from signal to production outcome, with humans approving the judgment calls at defined gates.

The Q4 2026 OKR commits to a thin slice of this vision: a walking skeleton, agents defined by config, the first Factory-completed issue, and a pilot of at least 20 completed issues. This PRD covers the full vision so that Q4 decisions do not block later phases, and it labels what is committed and what is not.

Engineers should start with the [working architecture](#3-working-architecture) and the [requirements](#4-requirements).

Human gates stay in front of every merge.

### 3.2 How a run flows

A Linear issue with the eligibility label reaches the intake Lambda, which authenticates and deduplicates it and starts a Temporal workflow. The workflow creates the run record in the ledger (this moment is "Factory first substantive work" for KR1), resolves the agent version from the agent index, and calls the execution host through an activity. The agent restores the repo snapshot, runs the harness, calls models only through the AI gateway, and calls tools only through AgentCore Gateway. It pushes a branch and opens the PR using the per-run token. It cannot merge. The workflow then waits for Gitar, Sonar, and human review as signals or timers, which can last days. A human merges. The workflow records the merge, rejection, or failure as the terminal event.

### 3.3 Agent definitions

Two things are kept apart. The **agent definition** is static and versioned in git. The **run request** is per invocation and thin. Definitions are built from open standards where they exist (AGENTS.md for instructions, Agent Skills for skill folders, and the Model Context Protocol (MCP) for tools) and mirror the AgentCore harness configuration field for field. The only part Fai defines is the governance envelope in the `fn` block.

```yaml
# agents/meeting_synthesis/agent.yaml  (illustrative values)
agentId: meeting_synthesis          # letters, digits, underscore; max 40
fn:
  owner: team:eng-leadership        # required: a named human or team
  host: harness                     # harness | runtime
  toolTier: 1                       # 1 read-only, 2 write or sensitive, 3 new MCP servers
  repos:
    - name: os-eng-leadership
      access: pr-only               # branch and PR, never merge
  triggers:
    - type: event
      name: transcript-dropped
  evals: ./evals/                   # gates every change to this definition
harness:                            # mirrors AWS::BedrockAgentCore::Harness
  model:
    provider: openAi                # routed through the AI gateway
    modelId: <gateway-model-alias>
  systemPrompt: ./instructions.md
  skills:
    - s3: { uri: s3://fai-skills/meeting-synthesis/ }
  allowedTools: ["@tier1/*"]        # guides the model only; Cedar enforces
  maxIterations: 40
  maxTokens: 50000
  timeoutSeconds: 1200
```

Every definition follows these rules. Every agent has a named owner. The tool tier is a request: Gateway policy and the generated identity and access management (IAM) role enforce it, so editing a definition cannot grant a tool by itself. Raising a tier or adding a tool target needs approval from the tool approval group. Changes to instructions, skills, or limits need the owner's review and passing evals. A run may narrow its definition, for example by lowering the spend cap, but it cannot add tools, raise the tier, or swap skills. The harness caps iterations, output tokens, and wall time. It has no dollar cap, so spend limits live in the AI gateway. Git tags use SemVer, AgentCore versions are integers, and the agent index maps one to the other.

### 3.4 Run contract

Every run, whatever host runs it, accepts the same request and returns the same result. The **request** carries only what varies per invocation: run_id, agent_id, agent_version (pinned at start), the trigger, inputs, target repos with refs, and optional overrides. The **result** carries what the ledger needs: status (succeeded, failed, blocked, or needs_human), failure reason, outputs (PR URL, files written, source links), trace_id, duration, tokens, cost, and a session reference so a human can resume where the agent stopped. The contract is the boundary that lets Runtime, the harness, or ECS and EKS change without changing the rest of the system.

### 3.5 Sandbox facts and limits

Runtime isolates each session in its own Firecracker microVM. Per-session compute is capped at 2 vCPU and 8 GB of memory, container images at 2 GB, and managed session storage at 1 GB. You cannot adjust those caps on the default microVM compute type. Maximum session lifetime is 8 hours (adjustable), with a 15-minute idle timeout (adjustable) and a 15-minute limit on synchronous requests. Larger working sets need EFS or S3 Files, and both require virtual private cloud (VPC) mode.

Runtime Instances (August 2026) is a second compute type that runs EC2 instances managed in our account, with sessions up to 14 days and VPC-only networking. The current documentation gives no instance sizes, so checking them is the first step in the fn-core question. EC2 itself has none of the Runtime caps, but isolation, startup, and teardown are ours to build.

Repo snapshots live in S3 and refresh on merge or on a schedule. A new session restores the snapshot and runs `git fetch` for the delta, which keeps startup short. Whether the fn-core sandbox image fits these limits is not yet known.

**Unverified:** whether the Strands harness, OpenCode, or pi can run a real coding task with MCP, git, and tests on Runtime. A third party has shown only a hello-world run. The security documentation available is the China-region version, so isolation, network, and audit behavior must be confirmed for our target region before production use.

### 3.6 Tripwires for moving off AWS

Move a component to another host behind the same run contract if any of these hold after testing on Runtime:

1. None of the Strands harness, OpenCode, or pi can run a real coding task in a Runtime container with MCP, git, and tests.
2. The 2 vCPU, 8 GB, or 2 GB image limits block the non-fn-core repo test, and neither EFS or S3 Files nor Runtime Instances fixes it.
3. Runtime cannot reach GitHub from VPC mode without an egress path that security accepts.
4. Per-run cost cannot be captured within a tolerance that Chuck and Cory set.
5. Temporal workers cannot run reliably on AgentCore, and ECS or EKS is needed. This moves the workers only, not the agents.

## 6. Measurement

The Q4 OKR requires several definitions to be fixed before the pilot. Those are the eligible issue set, acceptance criteria, issue start, Factory takeover, production attribution, the defect observation window, and the human baseline cohort. Until they are fixed, the KRs cannot be reported.

**KR1 (cycle time).** The median, in calendar days, from the Factory's first substantive work to an accepted, merged PR, across Factory-started eligible issues. Review wait is included. Blocked time is reported separately. The workflow records the start event at the Factory's first substantive work (proposed).

**KR2 (completions).** The count of eligible issues that meet acceptance criteria and merge through the standard gates. Unsuccessful attempts are recorded for operational analysis and are not scored as a KR.

**KR3 (quality).** Change failure rate is a deployment-level DORA (DevOps Research and Assessment) measure for Factory-attributed production deployments. If Factory changes are not deployed, the deployment measure is not applicable, and the escaped-defect ratio stands in. The escaped-defect ratio uses a fixed post-merge observation window. The team reports issues without a full window as pending, not as defect-free.

**Small numbers.** At a pilot of about 20 completions, percentage rates are volatile. Report the counts beside every rate, and do not claim a stable failure rate from a handful of deployments.

**Full-vision measures (not committed).** The brainstorm sets cost per accepted change as the headline measure, rolling up to cost per developed feature. That rollup needs a feature identity in the chain, a rule on whether human time is costed, and a rule for shared platform overhead. The 2027 roadmap draft also proposes CI duration as a metric. Neither is in the Q4 scope.
