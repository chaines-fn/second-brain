# Industry benchmarking for AI-DLC — AWS, and how the roles change

**Research question:** What is the industry doing with AI-native software development lifecycles (especially AWS/Amazon), and — beyond the Factory build itself — how does this change the day-to-day of software engineers, the software architect role, and product/UX, across a full end-to-end delivery model? What should Field Nation take from this for AI-DLC as a whole, not just the Factory workstream?
**Date:** 2026-07-09 (updated same day to add the role/end-to-end angle alongside the original AWS/architecture pass)
**Scope:** External/industry research only — no internal Slack, Confluence, or Linear search this pass (Chuck asked for the outside view; those connectors also weren't authorized in this session). First pass covered AWS, Google, and the technical PEV-loop architecture; this update adds the engineer role, the architect role, product management, and UX/design — i.e., the AI-DLC Process Transformation workstream, not just the Factory.

---

## Summary

The industry has converged on almost exactly the shape Field Nation has already designed independently: a spec-first planning stage, durable/versioned specs, agent execution against those specs, and a layered review stage (fast deterministic checks first, AI review second, human gate last). That's genuinely good news — it means the PEV loop, the Tier 1/2/3 knowledge layers, and the harness/infrastructure split aren't idiosyncratic bets, they're where everyone is landing. The vocabulary differs (AWS calls it "spec-driven development" and "steering," GitHub calls it a "constitution," Anthropic just calls it "the harness") but the architecture is the same.

AWS specifically has moved fast and is now shipping, as commercial products, several things Field Nation is currently planning to build bespoke. In December 2025, AWS announced three "frontier agents" — Kiro (autonomous coding agent), AWS Security Agent (design + PR + pen-test review), and AWS DevOps Agent (incident response) — that map almost one-to-one onto the Execute stage and parts of the Verify stage of FN's own architecture. Separately, Amazon Q Developer — AWS's previous coding assistant — is being sunset (end of support April 2027) in favor of Kiro, which is a live signal for anyone evaluating AWS tooling right now. Bedrock AgentCore, the runtime FN's current architecture candidate already leans on, has real enterprise traction (Nasdaq, Visa, Experian in production; 15x task growth in six months), which is a reasonable data point in favor of the AWS side of the M3 decision.

The most useful reality check came from an independent source, not a vendor: Thoughtworks' Birgitta Böckeler (whose "guides and sensors" vocabulary FN's own architecture doc already cites) tried Kiro, GitHub's Spec Kit, and Tessl hands-on and found real problems — verbose, one-size-fits-all workflows that turn a small bug fix into 16 acceptance criteria, specs that get generated but not actually kept up to date over time ("spec-first" but not "spec-anchored"), and agents that ignore their own instructions. That critique lands directly on the PRE-VERIFY task-contract idea Mykhailo proposed this week — a ticket-type-differentiated planning gate is a more sophisticated answer to a problem the commercial tools haven't solved yet, not a reinvention of something already solved.

On the "buy vs. build" question specifically: there's now a much stronger case for treating some of FN's planned Verify-stage sensors as things to buy rather than build. The AI code-review market alone is around $420M in ARR with real enterprise-scale players (CodeRabbit, Greptile) that already do PR-level and cross-file review — before FN builds a bespoke Code Review sensor, it's worth a quick look at whether one of these covers that layer more cheaply than building it.

Beyond the Factory build itself, the industry is describing the same role-level shift Field Nation's PEX Operating Model already anticipates, and confirms it in stronger, more specific terms than FN's own docs currently use. Software engineers are described as bifurcating into "orchestrators" who direct and validate agent work versus engineers whose main value was writing code, who become "redundant" — a starker framing than "humans orchestrate, agents execute," and one worth carrying into the change-management side of the Process Transformation workstream, not just the technical side. The Architecture Lead archetype Chuck's role already maps to is validated almost word-for-word by outside sources, with one concrete addition: evaluation-framework design (currently an unowned, TBD item in FN's Q2 deliverables) is showing up in industry material as a core architect responsibility, not a separate specialty — which is a reasonable argument for it landing explicitly on the Architecture Lead's plate rather than staying undefined. On the product and design side, the "prototype before you specify" principle FN already committed to is exactly where the industry has landed too, and there's a concrete, tactical pattern from product design practice — coded design systems plus a live, protected preview route inside the real app instead of a static Figma handoff — that's worth sharing directly with Ann-Bettina Colace's design team as the Process Transformation workstream's Step 3-4 tooling gets built out.

## Findings

### AWS is building — and selling — almost exactly FN's architecture

AWS's [frontier agents](https://www.aboutamazon.com/news/aws/amazon-ai-frontier-agents-autonomous-kiro) announcement at re:Invent 2025 (December 2, 2025) is the single most relevant industry data point for AI-DLC. AWS explicitly organized this around the software development lifecycle, not just coding: Kiro autonomous agent handles the build ("triaging bugs to improving code coverage," works "hours or days" with persistent context, opens PRs it doesn't self-merge), AWS Security Agent handles security review both pre-code (design doc review against org security standards) and post-code (PR scanning, on-demand penetration testing with auto-generated fix PRs), and AWS DevOps Agent handles the operations side (incident root-cause, with an internal Amazon claim of 86%+ root-cause identification accuracy and 3-5x faster resolution). Structurally, that's Execute / Verify(security) / and a post-production loop FN hasn't built yet — three of FN's planes as shipped products, not concepts.

This matters for the buy-over-build principle the team already committed to on 2026-05-05 ("buy whatever we can off the shelf... six months from now when it's no longer the right thing, we just buy the next thing and migrate it"). If the AWS platform decision lands on AWS, it's worth explicitly evaluating whether AWS Security Agent covers some or all of the Security Review sensor in FN's verification plane before building one, and whether AWS DevOps Agent is relevant to the steering-loop / root-cause-analysis concern flagged as a Q3+ item.

One important caveat: these are in preview, announced alongside enterprise reference customers (Clariant, Commonwealth Bank of Australia, SmugMug, Western Governors University, Presidio) that are larger or differently-shaped than FN. The claims (86% root-cause accuracy, penetration tests compressed from days to hours) are Amazon's own reporting on its customers, not independently audited. Directionally credible, but treat the specific numbers as marketing until FN can validate on its own workload.

### Amazon Q Developer is being sunset — a live signal, not history

Separately from Kiro's launch, AWS confirmed Amazon Q Developer (its previous-generation coding assistant) is being retired: new signups closed May 15, 2026, and IDE plugin/paid subscription support ends April 30, 2027, with Kiro as the explicit successor. If anyone at FN — inside or outside Moissanite — is currently using or evaluating Amazon Q Developer, that's worth flagging now rather than after the fact. It's also a useful data point on how fast the ground is moving under any single-vendor tool bet, which reinforces the harness/infrastructure separation the team already adopted (pick tools you can swap, not just once).

### Spec-driven development is the industry's name for FN's Plan/Spec stage — with real, documented failure modes

"Spec-driven development" (SDD) is the term the industry has settled on for spec-first planning before agent execution — this is functionally the same idea as FN's Spec (durable, versioned, sandbox-restartable contract) and the SDDF framing already in FN's architecture doc. Three tools implement it differently: [Kiro](https://kiro.dev/) (Requirements → Design → Tasks, three markdown files, "steering" docs for persistent context — product.md/structure.md/tech.md by default), [GitHub Spec Kit](https://github.com/github/spec-kit) (Constitution → Specify → Plan → Tasks, distributed as an open-source CLI across 14+ coding agents, more files and more process), and Tessl (still in private beta, aiming at "spec-as-source" where the spec, not the code, is the artifact humans edit).

The most valuable single source in this research was Thoughtworks Distinguished Engineer Birgitta Böckeler's [hands-on comparison of these three tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) — notable because FN's own architecture doc already cites her separate "guides and sensors" vocabulary, so this is the same voice FN is already building on. Her findings, in short: none of the three tools distinguish between problem sizes. Asking Kiro to fix a small, well-understood bug produced 4 "user stories" and 16 acceptance criteria — a sledgehammer for a small nut. Spec-kit produced so many repetitive markdown files that reviewing them took longer than just writing the fix would have. And critically, even with all that structure, the agents in her tests didn't reliably follow their own specs — one ignored notes that a class already existed and duplicated it.

This is directly relevant to Mykhailo's PRE-VERIFY proposal from earlier today (ticket-type-specific task contracts — bug vs. feature vs. chore, each with different first-checks). Böckeler's critique is effectively describing the exact gap that proposal closes: a one-size-fits-all spec step is the wrong shape for most real tickets. That's a point worth carrying into the Q3 planning conversation — it's not a "nice to have," it's addressing a documented, named failure mode in every commercial SDD tool tried so far.

### The harness/infrastructure split is now industry-standard framing, not an FN-specific insight

Anthropic's own enterprise guidance on Claude Code frames adoption the same way Chuck named it on 2026-05-05 (harness = how agents connect/orchestrate/execute; infrastructure = what they run on): reporting attributed to Anthropic's guidance states "the model does forty percent of the work, the harness does sixty," and that teams which invest in the harness (hierarchical CLAUDE.md files, hooks, skills, a maintained DRI) see multiplied productivity, while teams that just hand out model access don't. That's independent confirmation the FN team's mental model — buy the model/infra, invest engineering effort in the harness — is the right level to focus on, not a shortcut.

### Google's agent stack is maturing fast — relevant context for the still-open AWS vs. GCP call

At Cloud Next 2026, Google rebranded and merged Vertex AI and Agentspace into the "Gemini Enterprise Agent Platform" — a bundle of a code-first SDK (ADK, graph-based sub-agent orchestration, directly analogous to LangGraph), a managed runtime (Agent Engine), and an open cross-vendor protocol (A2A, now Linux Foundation-governed, "production-ready" as of Cloud Next 26 and reportedly running at ~150 enterprises). This doesn't change FN's existing AWS-leaning M3 signal, but it's worth knowing GCP's agent-hosting story is not standing still — Asad's existing AWS-vs-GCP comparative analysis on Confluence is likely still the more detailed source, this just adds a recent external data point that GCP's platform bet (ADK/Agent Engine) is real infrastructure investment, not a stalled offering.

### AI code review has become a real market — worth a buy-vs-build look before FN builds its own

Independent of any single cloud vendor, AI PR review tools (CodeRabbit, Greptile, and others) have scaled into a roughly $420M ARR category, with CodeRabbit alone reviewing 13M+ PRs across 2M+ connected repos, and Greptile differentiating on full-codebase indexing (catching cross-file/architectural issues that diff-only tools like CodeRabbit reportedly miss — relevant if FN Core's monolith structure ends up in scope). This is a direct candidate for (part of) FN's Code Review sensor in the verification plane — worth a short buy-vs-build spike before assuming it needs to be built from scratch, consistent with the Sonar precedent (buy the deterministic/mechanical layer, save inferential engineering effort for what's FN-specific).

### Real-world numbers are less impressive than benchmark numbers — useful for setting FN's own quality bar

Two data points worth internalizing before setting Q2/Q3 success targets: top coding agents score 74-78% on SWE-Bench Verified but real production PR-acceptance rates run 35-50% for the same agents — codebases have implicit conventions benchmarks don't test. Separately, Cognition (Devin) reports a 67% autonomous PR merge rate (up from 34% a year ago) — improving fast, but still meaningfully short of "just works." One industry report also flags that AI-generated PRs wait 4.6x longer in human review, meaning the human review gate — not agent capability — becomes the bottleneck once volume goes up. That's directly relevant to FN's own human-gate design (Plan Gate, PR Gate): the gates aren't just a quality safeguard, they're very likely to become the throughput constraint, and that's worth planning for explicitly rather than discovering it after rollout.

### The "AI Software Factory" framing isn't unique to FN

EY has launched "EY.ai PDLC" (Product Development Lifecycle), built with a partner called 8090, explicitly marketed with an "AI-powered factory line" metaphor for repeatable enterprise software delivery — the same metaphor FN used for over a year before the AI-DLC rebrand. Not a finding that changes anything technical, but useful context: the "factory" framing is apparently where multiple organizations independently landed, which is a mild data point that the metaphor was a reasonable one, whatever it's now called internally. EY's own framing for the underlying idea — "product development lifecycle," PDLC — is also worth noting as a close cousin of "AI-DLC" as a name, for whatever that's worth now that the name itself has been through three iterations in three days.

### The software engineer role: from producer to orchestrator, with a real bifurcation risk

Multiple sources converge on the same shift, though it's worth flagging that much of this content traces back to a small number of original opinion pieces (see Key Uncertainties) rather than fully independent research. The consistent description: the job moves from writing implementation code to "managing autonomous agents and auditing their output," with value increasingly concentrated in designing system architecture, defining objectives and guardrails for agents, and validating output — not in typing. One engineering director's account, offered as illustrative rather than representative, described a sprint where a team merged 40 PRs but engineers personally wrote only three, spending the rest of the sprint reviewing, arguing with the agent over testing frameworks, and catching hallucinated dependencies. The leading framing for how teams are organizing this in practice is "delegate, review, own": agents handle first-pass execution (scaffolding, implementation, tests, docs), engineers review for correctness/risk/alignment, and humans keep unambiguous ownership of architecture and outcomes — which is a clean, one-line description of exactly what FN's Engineering Operating Model principle "Humans Orchestrate, Agents Execute" and the Agentic Development Tiers table are already trying to operationalize.

The sharper and more uncomfortable framing worth carrying into the Process Transformation conversation: several sources describe this as a bifurcation, not a smooth transition — engineers whose value was defined by output volume are described as becoming "redundant," while engineers who can define ambiguous problems, catch architectural edge cases, and verify that a system solves the real business need become "more valuable than ever." FN's own docs describe the mechanics of the shift (tiers, DoR/DoD changes, review layers) but don't yet address the people side of that framing directly — worth thinking about deliberately as pilot-team rollout gets closer, since it's the kind of thing that generates quiet resistance if it's not named out loud.

### The architect role: FN's Architecture Lead concept holds up — and picks up one concrete new responsibility

What the industry says architects gain in this shift lines up almost point-for-point with what FN's overview.md already has under "How Chuck's Role Fits In": system design and architecture, defining acceptance criteria and quality thresholds for agents, reviewing/validating AI-generated output, governance and observability of agent workflows, and edge-case judgment. What decreases matches too — routine code authoring, boilerplate, first-draft documentation. The AGENTS.md convention (a standardized repo-level location for an agent's operating rules and constraints) that's called out repeatedly in industry material is functionally identical to what FN already calls CLAUDE.md/AGENTS.md in its Knowledge Layer section.

The one genuinely new, actionable data point: "evaluation framework design" shows up consistently as a core architect skill, not a QA or tooling specialty off to the side. FN's own architecture doc already lists an Eval framework as a Q2 deliverable but says its ownership is "TBD" (tooling, corpus, and scoring all unassigned as of the 2026-05-03 architecture doc). Industry framing is a reasonable argument that this isn't actually an open question — it belongs with the Architecture Lead, i.e., explicitly on Chuck's plate, not deferred as a separate hire or team.

Separately, the 2026 Gartner Magic Quadrant for Enterprise AI Coding Agents (Leaders: GitHub, Cursor, OpenAI) is evaluating vendors specifically on governance, permissions, and data access maturity — not just coding capability. That's a useful external validation for Ben Moormeier's InfoSec concerns from the April stakeholder walkthrough: the market's own evaluation criteria are converging on exactly what FN's non-negotiable Tier 2 skills and human PR gates are already designed to enforce.

### Product management: prototypes are replacing PRDs, which is exactly FN's Step 3-4 bet

Industry material describes product management's center of gravity moving upstream: with AI making code and documents cheap to produce, the valuable PM work becomes deciding what's worth building and what to ignore, not writing the PRD or waiting on an engineering queue. The concrete mechanism is the same one FN's PM Playbook already bets on — going from concept directly to an interactive, working prototype rather than a static requirements document, because a working prototype surfaces UX friction and produces real (if informal) user feedback that a document can't. This is a direct, specific validation of FN's Core Principle "Prototype Before You Specify" and the Step 3-4 compression (4-8 weeks down to 1-2) already documented in overview.md — the industry isn't just agreeing with the principle, it's converging on the identical mechanism.

### UX/product design: same "producer to evaluator" shift, plus a concrete tactical pattern worth sharing with design

Design is going through the same shift as engineering — one design-practice account (a builder at Intercom, interviewed for a design-focused newsletter, so treat as a single informed practitioner's account rather than a market survey) frames it as moving "from making to deciding": AI produces strong starting points fast, so a designer's time shifts from producing options to judging which direction is worth pursuing, and to the things AI still can't do well — motion, micro-interaction feel, taste. The same account also describes the classic "discover → define → deliver" double-diamond process as no longer needing to run in strict sequence, because building a working prototype is now fast enough to double as a discovery tool rather than only a validation step at the end.

The one specific, importable tactic: instead of a static Figma handoff, this practice sets up a coded design system with Figma Code Connect (mapping Figma components to their real code counterparts) and a protected `/design-space/` route inside the actual running application, so a designer's AI-built prototype renders with real navigation, real data, and real components — and a stakeholder reviewing it is looking at the real app, not a mockup. FN's overview.md doesn't currently have a design-specific tooling pattern for PEX Step 3-4 beyond "generates a working interactive prototype" — this is a concrete, low-risk pattern worth raising with Ann-Bettina Colace's team once Process Transformation tooling gets to that step.

### Team shape: small cross-functional pods over large siloed teams

Separate from the specific role changes, multiple industry sources describe a structural shift toward small (3-5 person) cross-functional pods replacing the traditional 8-12 person team split across separate product/design/engineering/data functions with layered handoffs between them — reasoning that AI collapses the cost of the handoff itself (a designer can hand over a working prototype instead of a spec; an engineer's agent can generate a first-draft test plan instead of waiting on QA). This is a relevant, if untested, data point for FN's still-open M2 pilot-team decision (Sapphire/Basalt/Diamond, or the Paper-Cuts-via-AI-DLC counter-proposal): it's not just which team, but how small and how cross-functional that team should be shaped, that the industry suggests matters.

## Key uncertainties

Vendor-reported outcome numbers (AWS's "78 days instead of 18 months," EY's "80x faster," Amazon DevOps Agent's "86% root-cause accuracy") come from the vendors themselves, describing their own reference customers, without independent audit or disclosed methodology. Treat as directional marketing, not benchmarks FN should plan against.

The PR-acceptance-rate research (35-50% real-world vs. 74-78% benchmark) came from aggregator/analysis sites rather than a primary academic or vendor source — the direction (real-world is worse than benchmarks) is very likely correct and matches general industry sentiment, but the exact percentages shouldn't be quoted externally without a primary source check.

I did not check FN's internal Slack, Confluence, or Linear for related discussion this pass — connectors weren't authorized for this session (Guru, Atlassian/Confluence, Linear, and Slack all need re-authorization; see note below), and the research direction Chuck asked for was explicitly external. If Asad's or Vitalii's recent work already covers Kiro, AgentCore, or frontier agents specifically, this report may be redundant with something already in Confluence — worth a quick internal search before circulating externally.

**Connector access note:** the Guru, Atlassian, Linear, and Slack connectors required re-authorization and weren't available in this session — that's a session-level auth issue, not a decision to skip them. They can be reconnected via claude.ai connector settings (or `/mcp` in an interactive session) if a follow-up pass should include internal sources.

**Source concentration on the "engineer/architect role" material:** several of the search results describing the engineer and architect role shift used near-identical phrasing ("designing the overarching system architecture, defining the precise objectives and guardrails... rigorously validating the final output") across supposedly independent articles. That phrasing traces back to a single CIO.com opinion piece (Lalit Wadhwa, EVP/CTO at Encora, Feb 2026) that appears to have been paraphrased or lightly reworded across several SEO/aggregator sites. Treat the engineer/architect role findings as substantially resting on that one industry-practitioner viewpoint plus the Gartner MQ and Anthropic material, not on many independently-arrived-at sources. The product-design account (Vitor Amaral/Intercom, via the Verified Insider newsletter) is a single practitioner's account, not a survey, and should be read the same way — directionally useful, not statistically representative.

The McKinsey figures cited in the engineer-role material (20-40% opex reduction, 12-14pt EBITDA margin increase for "AI-centric organizations") are second-hand via the CIO.com piece; the source McKinsey report itself wasn't independently fetched and verified this pass — worth doing before quoting that stat externally.
